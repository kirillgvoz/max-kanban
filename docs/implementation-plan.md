# Внутреннее ТЗ и рабочий промпт

## Решение по архитектуре

Каноническая реализация — `kanban/`:

- Go + Gin + PostgreSQL;
- React + Vite + TypeScript;
- MAX Bot API, webhook, WebSocket, RBAC, уведомления, миграции, тесты, Docker.

Каталоги `backend/` и `frontend/` в корне — ранний Python-прототип. Он сохраняется только как архивная ссылка, не участвует в итоговой сборке и не должен дублировать продуктовые требования.

## Цель

Подготовить конкурсную сдачу без дисквалификации и с запасом по технической оценке:

1. Воспроизводимый запуск одной командой через Docker.
2. Полные тесты backend и frontend.
3. Полная документация и формат сдачи по ТЗ.
4. Безопасность и отсутствие секретов в репозитории.
5. Проверка реального сценария в MAX.

## Рабочий промпт для самостоятельной реализации

```text
Действуй как ответственный за релиз инженер.

Работай только с каноническим стеком kanban/.
Не добавляй секреты в git.
Каждую доработку сопровождай тестом или проверяемой командой.
После изменений запускай:
go test -count=1 ./...
npm test
npm run build
docker compose build
docker compose up -d
Проверяй:
http://localhost:9300/max-kanban/api/health
https://kirillgvoz.ru/max-kanban/api/health
Фиксируй ограничения честно, а не скрывай их.
```

## Обязательные проверки

- `go test -count=1 ./...`
- `npm test` в `kanban/frontend`
- `npm run build` в `kanban/frontend`
- `docker compose build` в `kanban`
- `docker compose up -d` в `kanban`
- Проверка `/max-kanban/api/health` локально и через HTTPS
- Проверка webhook и MAX Bot API на фейковом и, при наличии токена, реальном контуре
- Проверка отсутствия секретов в staged-изменениях
