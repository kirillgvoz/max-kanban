# Масштабирование

Где потолки текущей архитектуры (с цифрами из кода), что масштабируется
просто добавлением реплик, а что потребует доработки. Все имена —
`kanban/` репозитория.

## Текущие лимиты (факты)

| Компонент | Поведение | Потолок |
|---|---|---|
| Воркер уведомлений (`services.Notifier`) | тик 5 с, **1** строка за `ProcessOnce`, пауза 500 мс после отправки | ~10–12 сообщений/мин на реплику |
| MAX Bot API | не более 2 сообщений/с в один диалог/чат/канал | наш пейсинг 500 мс — с запасом |
| Ретраи outbox | до 5 попыток, backoff `attempts²` минут, потолок 1 час, дальше `failed` | «отравленные» строки не крутятся вечно |
| Webhook-вход | stateless, лимит тела 1 МБ, дедуп по `webhook_events.event_key` | масштабируется репликами линейно |
| WS-тикеты | single-use, живут 30 с (`ws.Hub`) | переподключение = новый тикет |
| Планировщик дедлайнов | тик 1 час, ключи `task-deadline:<task>:<user>:<day>` | дубли между репликами невозможны |
| Миграции | advisory lock, таблица `schema_migrations` | конкурентный деплой N реплик безопасен |

Вывод: на одну реплику backend + Postgres в compose — это пилот на десятки
досок и чатов. Первым упрётся воркер уведомлений, вторым — WebSocket-хаб.

## Что масштабируется горизонтально уже сейчас

- **Webhook-обработчик** (`handlers/webhook.go`): состояния нет, идемпотентность
  в БД. Можно `docker compose up -d --scale backend=N` за балансировщиком —
  повторные доставки MAX разложатся по репликам и отфильтруются ключами.
- **Воркер уведомлений**: `claimNext` через `FOR UPDATE SKIP LOCKED` —
  две реплики не заберут одну строку. Каждая реплика даёт +~10 msg/min.
  Глобальный порядок между диалогами не гарантируется (и не нужен).
- **Планировщик дедлайнов и миграции**: безопасны при N репликах (ключи
  + `ON CONFLICT DO NOTHING`, advisory lock).

## Что мешает: WebSocket-хаб в памяти

`ws.DefaultHub` — `map[orgID]clients` + тикеты **в памяти процесса**
(`ws/hub.go`):

1. Клиент обязан попасть на ту же реплику для `POST /api/ws-ticket` и
   `GET /ws?ticket=...` — иначе тикет не найдётся. Нужен **sticky sessions**
   (в Nginx — `ip_hash` upstream).
2. `BroadcastToOrgDirect` с реплики A не видит клиентов на реплике B —
   часть браузеров пропустит `task:created`/`task:moved`.

Варианты по мере роста (сейчас не реализовано):

- оставить 1 реплику-«держателя WS» + N stateless API-реплик (быстро, но SPOF);
- вынести fan-out в Redis Pub/Sub или Postgres `LISTEN/NOTIFY`: broadcast
  пишет в канал, каждая реплика досылает своим клиентам (правильный путь);
- тикеты — в Redis/БД с TTL вместо `map`.

## База данных

- Пул — `pgxpool` с дефолтами; крутится через `DATABASE_URL`, параметры пула
  задаются в нём же (`pool_max_conns`, `pool_min_conns`, ...). При росте числа
  реплик backend поднимать `pool_max_conns` и `max_connections` Postgres
  согласованно, иначе реплики начнут ждать коннекты.
- Уникальные ключи `webhook_events.event_key` и `notification_outbox.event_key`
  — горячие точки записи; это узкие `INSERT ... ON CONFLICT`, для пилота
  достаточно.
- Код использует **один пул на чтение и запись** — read-replica из коробки
  не поддерживается, это точка роста при сотнях RPS на списки досок/задач.
- Данные — в volume `pgdata`; бэкап/рестор — `scripts/backup.sh` /
  `scripts/restore.sh` (см. `docs/operations.md`). Следующий шаг —
  managed Postgres с PITR вместо файловых дампов.
- Тяжёлые места при росте: `chatStatus` (`COUNT ... FILTER` по задачам чата)
  и списки задач доски — первыми кандидатами на индексы/пагинацию.

## Тюнинг воркера уведомлений

`Interval` (5 с), `RateLimit` (500 мс), `MaxRetries` (5) — константы
`NewNotifier` в коде: тюнинг = правка + `scripts/rebuild.ps1`. Правила:

- не опускать глобальную паузу ниже ~500 мс без per-dialog шейпера — иначе
  упрёмся в лимит MAX 2 msg/s на горячих чатах;
- для всплесков (массовая смена статусов) дешевле добавить реплику backend,
  чем ускорять тик: `SKIP LOCKED` уже распараллеливает;
- `failed`-строки не перезапускаются сами — нужен ранбук: смотреть
  `last_error` в `notification_outbox` (протухший токен, удалённый чат,
  непривязанное приложение) и чинить причину, а не ретраить вслепую.

## Мониторинг под рост

- `GET /max-kanban/api/health` — `status` + `database` (живость для
  балансировщика).
- `GET /api/metrics` (авторизованно): `notification_outbox.pending/sent/failed`,
  `websocket_clients`, `schema_migrations`.
- Алерты: рост `pending` (воркер не успевает / MAX недоступен), `failed > 0`,
  всплеск `webhook ... error` в логах, строка `open_app button rejected`
  (напоминание привязать URL в панели, а не авария — текст доходит).
- Логи Werner: `docker compose logs backend --tail=100`; события чатов всегда
  можно сверить с `webhook_events` в БД.

## Лестница масштабирования

1. **Пилот** (сейчас): 1 backend + Postgres в compose, всё в одном бинарнике
   (API, WS, webhook, воркер, планировщик, SPA).
2. **Больше уведомлений**: 2–3 реплики backend за Nginx; WS пока на одной
   (sticky), либо принять пропуски broadcast при переподключении.
3. **Много живых досок**: `pool_max_conns`, managed Postgres, Redis/ PG NOTIFY
   для WS fan-out, тикет-стор вне памяти.
4. **Регионы/HA**: внешний Postgres + PITR, бот-токен один (лимиты MAX общие),
   вебхук один — реплики только за ним; шардировать тут нечего, бутылочное
   горлышко — API MAX, не мы.
